# Alternatives and baseline drafting

Read for a genuine solution choice or substantive initial drafting. The root owns alignment, state and revision limits; the inquiry module supplies optional mechanism-changing moves.

## Compare alternatives under one contract

An alternative must differ in operating principle, roles/authority, workflow, technical configuration or allocation of cost/risk. Renaming features is not enough. By default briefly develop two or three candidates, honoring any user-specified count. Do not manufacture alternatives for a fixed calculation, translation or local edit.

For each candidate record core mechanism, changed premise versus other candidates, fixed requirements, prerequisites/resources/permissions, advantages, weaknesses and suitable conditions. Distinguish a condition that must hold from evidence it does hold. Do not turn unsupported forecasts into precise scores.

Compare on the same objective, constraints and priorities. Use one to three shared situations that expose meaningful differences, rather than a quota of repetitive scenarios. Record judgment and key reason for each comparison. Explain the preferred candidate and the observable conditions that would change the choice.

Choose one baseline only within delegated criteria and authority. Use Q for a user-owned decision or an ambiguous interpretation, E for a decisive unknown. An attractive reframe does not grant permission to solve a different problem.

## Avoid premature commitment and uncontrolled branching

Keep unselected concepts brief; preserve only the runner-up's mechanism and reconsideration conditions. Do not fully implement or continuously improve every candidate. Multiple alternatives applied to multiple scenarios are evaluations, not separate revisions. If multiple final options were requested, the set remains the single deliverable.

Combine strengths only after checking assumptions, permissions, interfaces and structures are compatible. If all candidates fail hard constraints, identify the shared or distinct reasons. Seek needed facts/decisions via E/Q. For fixable candidate defects, register the reviewed set as the initial deliverable and improve it through M. Do not choose arbitrarily, relax requirements, declare all conceivable solutions impossible, or generate endless new sets without evidence.

## Draft what the mechanism actually requires

D creates the initial draft. Changes to an existing deliverable, including replacement after re-exploration, use M and the root's counters. Specify necessary inputs, owner/authority, processing rules, outputs, handoffs, exceptions and acceptance behavior at the level the task requires.

For early ideation, evaluate differentiation and hard constraints before requiring rollout detail. For an execution plan, incomplete implementation conditions remain real gaps; do not invent them later during verification. Prefer the simplest sufficient mechanism without speculative infrastructure. After drafting, use V.
